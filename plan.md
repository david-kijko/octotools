## 1. Why this experiment exists

The spec's hypothesis is explicit: replacing octotools' text-JSON `toolbox_metadata` with `/imagegen`-rendered PNG tool cards, and optionally adding `/imagegen` + `hephaestus2` adversarial plan review, may measurably change end-to-end accuracy or efficiency on MathVista, MedQA, and GAIA-Text. The sign is unknown; this is an empirical test, not a foregone product direction. The baseline octotools loop currently analyzes the query, predicts a next tool step, generates a command from text metadata, executes the tool, verifies memory, and finally emits `direct_output`.

This harness exists so future hephaestus2 implementers can run the experiment without re-reading the entire repository or accidentally implementing unrelated Simplement template prose. The scoped outcome is a three-branch, 90-query early sample using `gpt-4o-mini-2024-07-18` where reviewers compare A/control, B/image tool cards, and C/image cards plus adversarial plan review before deciding whether to escalate to a larger Tier-1 benchmark.

## 3. Architecture hooks in octotools

### Current per-query loop

The reusable package loop in `octotools/solver.py` is:

1. `Planner.analyze_query(question, image_path)` at `octotools/solver.py:73`.
2. Main step loop begins at `octotools/solver.py:80` / `octotools/solver.py:83`.
3. `Planner.generate_next_step(...)` predicts `(context, sub_goal, tool_name)`.
4. `Executor.generate_tool_command(...)` receives `self.planner.toolbox_metadata[tool_name]`.
5. Tool execution writes into `Memory`.
6. `Planner.verificate_context(...)` decides whether to stop.
7. `Planner.generate_direct_output(...)` writes `direct_output` when requested.

`tasks/solve.py` contains a second benchmark-local `Solver` with the same broad flow, and the benchmark smoke commands call that file directly. See **GOTCHA-01** before implementing C-2; the plan-review insertion point must affect the benchmark runner, not only the package solver.

### Prompt sites changed by Branch B

Branch B rewires the four text-metadata prompt surfaces:

- `octotools/models/planner.py::analyze_query` — currently interpolates `Metadata for the tools: {self.toolbox_metadata}`.
- `octotools/models/planner.py::generate_next_step` — currently interpolates `Tool Metadata: {self.toolbox_metadata}` and calls text-only `self.llm_engine`.
- `octotools/models/planner.py::verificate_context` — currently interpolates `Toolbox Metadata: {self.toolbox_metadata}`.
- `octotools/models/executor.py::generate_tool_command` — currently receives one selected tool metadata dict and creates a fresh text-only LLM engine.

The B slice creates `octotools/models/toolbox_renderer.py`, commits PNG cards under `octotools/tools/_cards/`, passes `toolbox_mode` through solver/initializer boundaries as needed, and replaces metadata text with image attachments rather than appending images beside the old text. Because the spec names `gpt-4o-mini-2024-07-18` as a multimodal engine, planner and executor calls that see card images must route through multimodal LLM invocation.

### Plan-review insertion changed by Branch C

Branch C inserts `plan_review_loop(max_rounds=2)` after `analyze_query` and before the main step loop. In the package solver that means after `octotools/solver.py:73` and before `octotools/solver.py:80`; in benchmark execution it must also be visible from `tasks/solve.py` because `tasks/run_octotools.sh` scripts execute `python solve.py` from inside `tasks/`.

C creates:

- `octotools/integrations/imagegen_runner.py` — true subprocess wrapper around `hephaestus --file <brief> --dangerous`; output path is written inside the brief, matching the patched Simplement bootstrap contract.
- `octotools/integrations/hephaestus2_runner.py` — subprocess wrapper using `HEPHAESTUS_MODEL=gpt-5.5 HEPHAESTUS_REASONING_EFFORT=high` for adversarial critique.
- `octotools/models/plan_review.py` — plan diagram orchestration and review loop.
- `Planner.generate_structured_plan(...)` — emits ordered `(tool, sub_goal, depends_on)` triples.

## 4. Operator surface

Reviewers operate the experiment through the existing benchmark scripts plus branch-specific worktrees:

| Branch | Script surface | Required task cells | Result surface |
|---|---|---|---|
| A/control | `tasks/mathvista/run_octotools.sh`, `tasks/medqa/run_octotools.sh`, `tasks/gaia-text/run_octotools.sh` on `main` | 10 indices per task; spec index set is `100,110,...,190` | Per-query `output_<index>.json`, score logs, final `verdict.md` row |
| B/image cards | Same three scripts from `/home/david/Projects/octotools-img-toolcards` | Same 30-query sample | Direct-output accuracy, steps, calls, tokens, wall-clock, cost, tool usage |
| C/adversarial plan | Same three scripts from `/home/david/Projects/octotools-img-toolcards-adv-plan` | Same 30-query sample | Same metrics plus `plan_review` evidence per query |

The intended grid is 3 branches × 3 tasks × 10 indices = 90 queries. Existing scripts do not yet encode that exact grid for every task; **GOTCHA-03** records the mismatch. The final operator artifact is `verdict.md`, containing the reporting grid from the spec and a recommendation: escalate to Tier-1 if the accuracy delta is at least 3 percentage points on at least two tasks for B or C; otherwise close or iterate.

## 5. What this experiment does NOT do

- It is not a refactor of octotools; changes must stay surgical around metadata rendering and plan review.
- It is not performance tuning; no prompt caching, async tool execution, verifier merging, or runner pooling belongs in these slices.
- It is not a Tier-1 or Tier-2 full benchmark; this harness only prepares the early 90-query sample and verdict gate.
- It does not regenerate [`docs/octotools-architecture.png`](./docs/octotools-architecture.png) or [`docs/octotools-implementation-path.png`](./docs/octotools-implementation-path.png).
- It does not modify the design spec; if code evidence contradicts the spec, update [`Gotchas.md`](./Gotchas.md) and the relevant slice brief instead.

## 6. Implementation strategy

1. **B-1 — Image tool cards.** Fork `exp/img-toolcards` from `research/imagegen-toolcards`, generate the union tool-card PNGs once with `/imagegen`, add `toolbox_renderer.py`, and rewire planner/executor prompt sites. Gate: diff stat, PNG validity, MathVista index 100 direct-output smoke, verbose evidence of image attachments.
2. **C-1 — Runtime wrappers.** Fork `exp/img-toolcards-adv-plan` from B after B passes. Add thin `hephaestus` subprocess wrappers only; no solver consumption yet. Gate: one real PNG from `imagegen_runner.generate_image` and one non-empty critique from `hephaestus2_runner.critique`.
3. **C-2 — Plan review.** Add structured plan generation and the two-round review loop between analysis and step execution. Gate: diff stat, MathVista index 100 direct-output smoke with `plan_review`, stdout `[plan_review] round=N`, and a non-empty diagram PNG under `/tmp/octotools-plan-diagrams/` or equivalent.

See [`slices/README.md`](./slices/README.md) for the left-to-right dependency graph and exact branch/worktree rules.
